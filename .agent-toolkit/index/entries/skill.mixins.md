- Before writing a mixin, look for a GTCEu or NeoForge mechanism; a mixin is for what has none. Features on existing machines (traits, UI buttons): MachineFeatures (api.machine-features). Recipe behaviour of a GT recipe type: a custom recipe logic runner added at setup (PotionMixBrewingLogic). Machine definition values that stay live, e.g. output limits: edit them at setup (SteamTweaks). Recipe viewer slots: RecipeTypeLayouts. Several changes to one target class go in one mixin.
- Mixin classes live in core/mixins/ (ae2/, recipedb/; workarounds for GTCEu/MUI bugs in gtceufix/, deleted once upstream fixes them, see gtceufix.overview). Only mixin classes in a config's package; helpers go elsewhere (e.g. common/recipedb/), else loading fails.
- Plain mixins: gtmqol.mixins.json. Its plugin GTMQoLMixinPlugin only handles overclocking.overhaul and skips by class name, so anything else added to those OC mixins disappears with the overhaul off.
- A set that must switch on/off as a whole gets its own config whose plugin decides in shouldApplyMixin (gtmqol.recipedb/ae2/jeifix.mixins.json). Plugins extend GTMQoLMixinConfigPlugin (no-op defaults, isModLoading for mods not constructed yet). Register new configs in neoforge.mods.toml [[mixins]] (1.20.1: build.gradle mixin { config ... }).
- Mixin configs load before any mod is constructed, so GTMQoLConfig can't be read there. Startup switches go in config/gtmqol-early.properties via java.util.Properties (EarlyConfig, like GTCEu's gtceu-early.properties). Changes that can't be undone at runtime (@Overwrite etc.) get such a switch or none.
- Private/package-private types: @Accessor matches the field descriptor, so the return type can't be Object in place of an invisible type; the target object can be cast to Object then to the accessor interface (@Mixin(targets = "...$Inner")). A field of the mixin's own target class needs no accessor: @Shadow it.
- Lambda targets: javac's synthetic name (lambda$getNext$0) or a regex (/^lambda\$/); recheck after GTCEu bumps.
